# SYEV/SYEVX regression hunt + full retune: multi-subagent workflow plan

Target: recover the "we beat cuSOLVER for all n = 32–512" state, decide which small-n kernel
runs for n = 4–32, retune every tuning constant and switch point, remeasure at saturation, and
then work the remaining ideation backlog.

This document is the execution plan for a `Workflow` run. It is written to be handed to
subagents verbatim.

---

## 0. The lead: a shadowed tuning header

**Verified by inspection, not yet by measurement.** This is the primary regression hypothesis
and Phase 1 exists to confirm or kill it.

There are two files that both answer `#include <batchlas/tuning_params.hh>`:

| Path | Origin | ORMQR block sizes | SYTRD block sizes |
|---|---|---|---|
| `include/batchlas/tuning_params.hh` | **checked into git**, header says "auto-generated … Source profile: `build/tuning/profile.json`" | **16, 16, 16, 16, 16** | 8, **8, 16, 24, 32** |
| `${PROJECT_BINARY_DIR}/include/batchlas/tuning_params.hh` | generated by CMake from `cmake/tuning_params.h.in` | 16, **32, 64, 128, 128** | 8, **16, 32, 64, 64** |

`src/CMakeLists.txt:75-79` lists the include directories in this order:

```cmake
$<BUILD_INTERFACE:${PROJECT_SOURCE_DIR}/include>     # <-- committed header, wins
$<BUILD_INTERFACE:${PROJECT_BINARY_DIR}/include>     # <-- generated header, shadowed
```

So the committed header **shadows the generated one on every build**. The CMake defaults in
`cmake/BatchLASGeneratedHeaders.cmake:41-50` are dead code, and so is any profile-driven
retune written to the binary dir by `batchlas_tuning_header`.

Corroboration that the committed values are what actually executes: the comment added by
`f7f3c57` in `src/extensions/sytrd_sy2sb.cc:32` observes at runtime that "Every
`ORMQR_BLOCK_SIZE_*` constant is 16, so a kd=32 panel is split into two WY blocks". That is
the committed header's value, not the generated one's.

**Why this maps onto n = 32–512 specifically.** The bucket boundaries are
`n≤64 TINY / n≤128 SMALL / n≤256 MEDIUM / n≤512 LARGE / else XLARGE`. Across exactly the
range the user reports as regressed:

- `ORMQR_BLOCK_SIZE_SMALL` 32 → 16 (2× narrower WY block)
- `ORMQR_BLOCK_SIZE_MEDIUM` 64 → 16 (4×)
- `ORMQR_BLOCK_SIZE_LARGE` 128 → 16 (**8×**)
- `SYTRD_BLOCK_SIZE_SMALL` 16 → 8, `MEDIUM` 32 → 16, `LARGE` 64 → 24

The back-transform is `2n³` of the `~4.7n³` total, and it is the part that should be pure
GEMM. Running it at k=16 instead of k=128 is precisely the shape that turns a compute-bound
BLAS-3 phase into a launch- and bandwidth-bound one.

**Suspect commits**, in order of likelihood:
- `7363746` (2026-03-02) "Generate compile-time tuning constants from tuning profiles" —
  introduced the committed header with ORMQR flattened to 16.
- `91341c1` (2026-03-31) "refactor device BLAS headers and call sites" — moved
  `SYTRD_BLOCK_SIZE` to 8/8/16/24/32.
- `0c9f195`, `6c2664a` — STEDC constants only.

**Two failure modes to keep separate.** (a) The values are wrong. (b) The *mechanism* is
wrong — a committed artifact shadowing a generated one means no retune can ever take effect,
which makes every later phase of this plan pointless until fixed. (b) must be fixed first
regardless of what (a) measures.

## 1. Hard constraints every agent must obey

These are not style preferences. Violating any of them silently produces numbers that look
fine and are wrong.

### 1.1 The GPU is a serializing resource

The machine has **two RTX 4090s** (`nvidia-smi` indices 0 and 1). Therefore:

- **At most two measurement agents run concurrently**, each pinned to a distinct device.
- Pin with `ONEAPI_DEVICE_SELECTOR` and `CUDA_VISIBLE_DEVICES` together; assert inside the
  agent that the selected device index matches what was requested.
- **Never** compare an A arm measured on device 0 against a B arm measured on device 1.
  Both arms of any comparison run on the *same* device, interleaved.
- Analysis/reading agents (no GPU) fan out freely — that is where workflow parallelism goes.

The workflow structure is therefore: **wide fan-out for reading, a two-lane serialized
pipeline for measuring.** Any agent that both reads and measures must be split in two.

### 1.2 Batch saturation is mandatory, and it must be measured, not assumed

The user has stated this repeatedly and prior work has been burned by it. An unsaturated
ratio measures launch overhead, not the algorithm.

Saturation is **not** a constant. It depends on the work-group count the kernel actually
launches, which for the batch-parallel kernels is `batch`, and for the CTA kernels is
`batch × cta_wg_size_multiplier`. RTX 4090 has 128 SMs.

**Phase 2 produces a measured saturation table** and every later phase reads it:

> For each (kernel, n, type, jobz), sweep `batch` over 1, 2, 4, …, 2048 and record µs/matrix.
> The saturation batch is the smallest batch at which µs/matrix is within **5 %** of the
> minimum over the remaining sweep. If µs/matrix never flattens, report `unsaturated` and
> the sweep is extended; do not pick a number.

All head-to-head comparisons run at `max(saturation_batch(A), saturation_batch(B))`.

### 1.3 Benchmark-name matching

`--name` in `include/util/minibench.hh` is a **substring** filter. `--name=BM_SYEV` also runs
`BM_SYEVX`, `BM_SYEV_Crossover`, everything. This has already corrupted one published grid
(the correction is recorded in `include/blas/functions/syev.hh:146`).

Every agent must key result rows on the **`name` column of the CSV**, not on the flag it
passed, and must assert that the set of distinct names in the output is exactly the set it
intended to run.

### 1.4 Measurement hygiene

- Confirm both GPUs are idle before a run (`nvidia-smi`); abort if another process holds
  memory on the target device.
- Discard the first timed repetition (cold clocks). Prefer the harness's own warmup if it has
  one; otherwise run the shape once untimed.
- Report **median of ≥ 5 rounds** with the interquartile range, not a single mean. A/B arms
  must be **interleaved** (ABABAB…), never run as one block then the other.
- A claimed win under **1.10×** with overlapping IQRs is reported as *neutral*, not as a win.

### 1.5 Build discipline

- One shared CUDA build directory per *code state*. Agents that only flip environment
  variables share a build; agents that change a header get their own build.
- **Every tuning-constant experiment must be runnable without a rebuild**, or the sweep is
  untenable. See Phase 3.0 — the first coding task is to make the constants
  environment-overridable, precisely so the rest of the sweep is env-only.

### 1.6 Correctness gate

The test suite baseline is **not green** on `main` (lanczos/stedc/steqr fail; `syev_cta` is
flaky under `-j4`). Agents must diff subtest names against a captured baseline, never against
"all pass". Phase 1 captures that baseline once; every later verification diffs against it.

Use the selective-testing policy: `ctest -L`/`-LE slow` and `--gtest_filter`, full suite only
before the final push.

## 2. Workflow phases

Nine phases. Phases marked **[GPU]** are serialized into the two-lane pipeline; phases marked
**[CPU]** fan out freely.

### Phase 1 — Foundation (serial, 1 agent, ~1 build)

Deliverable: a working CUDA build, a captured test baseline, a captured device inventory.

1. `cmake --preset cuda && cmake --build --preset cuda -j` (see `CMakePresets.json:54`).
   The existing `build/` is CPU-only (`BATCHLAS_ENABLE_CUDA:BOOL=OFF`) and must not be reused.
2. Record: SM count, clocks, driver, cuSOLVER version, both device indices.
3. Run the eigensolver-relevant tests once and **commit the pass/fail list as the baseline**:
   `syev_tests`, `syev_cta_tests`, `syev_cta_fused_tests`, `syev_jacobi_cta_tests`,
   `syev_blocked_tests`, `syev_two_stage_tests`, `syevx_tests`, `stedc_tests`, `steqr_tests`.
   Run single-threaded to avoid the known `syev_cta` `-j4` flakiness.
4. Emit the machine-readable baseline as JSON for later phases to diff against.

Gate: if the CUDA build fails, the whole workflow stops here and reports. Nothing downstream
is meaningful without it.

### Phase 2 — Saturation table **[GPU]** (2 lanes)

Deliverable: `saturation.json`, consumed by every later phase.

Sweep `batch ∈ {1,2,4,8,16,32,64,128,256,512,1024,2048}` for:

- providers: `Vendor`, `BatchLAS_CTA`, `BatchLAS_Blocked`, `BatchLAS_TwoStage`
  (forced via `BATCHLAS_SYEV_PROVIDER`), plus `syev_cta_fused` and `syev_jacobi_cta` through
  their own benchmark targets
- `n ∈ {4, 8, 16, 24, 32, 48, 64, 96, 128, 192, 256, 384, 512}`
- `T ∈ {float, double}`
- `jobz ∈ {NoEigenVectors, EigenVectors}`

Apply the §1.2 rule to derive the saturation batch per cell. Report any cell that never
saturates.

This phase is large but embarrassingly parallel **across the two devices only**. Split the
(n, type) grid into two halves, one per lane.

### Phase 3 — Regression forensics

**3.0 [CPU] Make the tuning constants runtime-overridable.** *This is the enabling code
change for everything after it and must land first.*

Replace the `constexpr` reads in `tuning_params.hh`'s `*_for_n()` accessors with functions
that consult an environment override and fall back to the compiled constant, following the
existing convention in the codebase (`BATCHLAS_SY2SB_ORMQR_NB`, `BATCHLAS_SYEV_TWO_STAGE_KD`
— read fresh on each call so one process can A/B):

```
BATCHLAS_TUNE_ORMQR_BLOCK_SIZE=<int>     # overrides ormqr_block_size_for_n
BATCHLAS_TUNE_SYTRD_BLOCK_SIZE=<int>
BATCHLAS_TUNE_LATRD_WG_HINT=<int>
BATCHLAS_TUNE_STEDC_RECURSION_THRESHOLD=<int>
BATCHLAS_TUNE_STEDC_MERGE_VARIANT=<int>
BATCHLAS_TUNE_STEDC_THREADS_PER_ROOT=<int>
BATCHLAS_TUNE_STEDC_WG_MULTIPLIER=<int>
```

Constraint that bites: several of these feed `*_buffer_size` queries as well as the solve.
An override must be read **identically in both**, or the workspace desynchronises from the
block width — the exact failure `two_stage_common.hh:73` warns about. Add a test that asserts
buffer-size/solve agreement under each override.

Unset ⇒ bit-for-bit current behaviour.

**3.1 [CPU] Resolve the shadowing.** Decide and implement one of:
- (a) delete the committed `include/batchlas/tuning_params.hh` and let the generated header
  be the only one — cleanest, but breaks any consumer building without CMake;
- (b) reorder the include dirs so `PROJECT_BINARY_DIR` precedes `PROJECT_SOURCE_DIR` — a
  one-line fix that silently changes every constant, so it must land *with* Phase 3.3's
  measurements, not before them;
- (c) keep the committed header as the single source of truth and delete the generator +
  CMake defaults — honest, and eliminates the class of bug permanently.

Recommend **(c)** unless the tuning pipeline is actually in use; verify that first by
checking whether `build/tuning/profile.json` is ever produced. Whichever is chosen, the
outcome must be that **exactly one file can supply these constants.**

**3.2 [CPU] Archaeology.** Bisect the committed header's history for the ORMQR and SYTRD
values, confirm `7363746` and `91341c1` as the introducers, and check whether either commit
carried a measurement justifying the change or merely regenerated a profile. Report which.

**3.3 [GPU] The decisive A/B.** With 3.0 landed, at the saturation batch from Phase 2, for
`n ∈ {32, 64, 128, 256, 384, 512}`, both types, both jobz, measure BatchLAS vs cuSOLVER at:
- arm A: committed values (ORMQR 16, SYTRD per-bucket committed)
- arm B: CMake-default values (ORMQR 16/32/64/128/128, SYTRD 8/16/32/64/64)

If B beats A across n = 32–512, the hypothesis is confirmed and Phase 5 becomes "restore and
then tune". If B does not, **say so plainly and move to 3.4** — do not tune around a
disproved theory.

**3.4 [GPU, conditional] Widen the hunt.** Only if 3.3 fails to explain the gap. Bisect
`syev` performance at n = 256 saturated across the commits between the last known-good state
and `main`, using the routing-forced provider so the bisect measures the kernel and not the
routing. Candidate non-tuning suspects: `ab1de6e` ("Optimize CTA and blocked eigensolver
kernels"), `91341c1`, `8c81bd4`.

### Phase 4 — Small-n bake-off, n = 4–32 **[GPU]**

Deliverable: a per-(n, type, jobz) winner table and a routing rule.

Four contenders: `syev_cta`, `syev_cta_fused`, `syev_jacobi_cta`, `Vendor`.
Sweep `n ∈ {4, 6, 8, 12, 16, 20, 24, 28, 32}` × `T ∈ {float, double}` ×
`jobz ∈ {values, vectors}` × `cta_wg_size_multiplier ∈ {1, 2, 4, 8}`, at the saturation batch.

Report best-of-multiplier per kernel *and* the best multiplier, since the multiplier is
itself a tuning constant that should end up in the routing rule.

Known priors to confirm or overturn, from `JACOBI_EIGENSOLVER_PLAN.md` §13.2:
- double: Jacobi 1.2–3.8× faster than `syev_cta` at every n ≤ 32
- float: Jacobi wins to n=16, loses at n=32 (0.40–0.61×)
- **caveat that must be restated in the output**: part of the double margin is the 4090's
  1/64 FP64 rate, so the double rule is hardware-specific and should be gated on measured FP64
  throughput rather than on the scalar type.

`syev_cta_fused` has **no** in-tree head-to-head measurement. This phase produces the first
one. Outcome is binary: route it, or open a follow-up to retire it.

Accuracy is a gate, not a tiebreak: any kernel routed by default must pass the existing
tests, and Jacobi's graded-SPD relative-accuracy advantage (4.5e-07 vs 2.7e+28) is a reason to
prefer it on ties, not a reason to accept a slowdown.

### Phase 5 — Retune the mid-range constants, n = 32–512 **[GPU]**

Env-only sweeps, enabled by 3.0. One agent per constant, but **serialized through the two GPU
lanes** — they are not independent of each other, so the sweep is coordinate descent, not a
free fan-out:

1. `ORMQR_BLOCK_SIZE` ∈ {16, 32, 64, 128, 256} — largest expected effect, do first
2. `SYTRD_BLOCK_SIZE` ∈ {8, 16, 24, 32, 48, 64}
3. `LATRD_LOWER_PANEL_WG_HINT` ∈ {0, 64, 128, 256} (and interacts with the grid path — see
   Phase 6)
4. `STEDC_RECURSION_THRESHOLD` ∈ {16, 32, 64, 128}, `STEDC_MERGE_VARIANT`,
   `STEDC_THREADS_PER_ROOT`, `STEDC_WG_MULTIPLIER`

Two passes of coordinate descent, then one confirmation run of the joint optimum against the
per-coordinate optima. Report if the joint point is *not* the composition of the individual
optima — that is the signal that the parameters interact and a proper joint search is needed.

Bucket boundaries (64/128/256/512) are themselves tunable and should be re-derived from the
per-n optima rather than assumed.

### Phase 6 — Two-stage and grid-latrd retune **[GPU]**

1. Re-sweep `BATCHLAS_SYEV_TWO_STAGE_KD` ∈ {16, 32, 48, 64, 96, 128} **with the
   `BATCHLAS_SY2SB_ORMQR_NB` hint active**. The committed kd=32 optimum
   (`two_stage_common.hh:38`) was measured under the split-WY behaviour that `f7f3c57`
   removed, which structurally penalised wide bands. Literature and MAGMA both put the
   eigenvector optimum at 96–128.
2. Re-derive `BATCHLAS_SY2SB_ORMQR_NB`'s shape gate (currently n ≥ 1024 & batch ≥ 32) at the
   new kd.
3. Re-measure `BATCHLAS_LATRD_GRID_MIN_N` (currently 768) **in eigenvector mode** — it was
   derived eigenvalues-only and is applied in both. Split the constant per mode if the
   crossovers differ.

### Phase 7 — Re-derive every switch point **[GPU]**

With Phases 3–6 landed, every routing threshold in `include/blas/functions/syev.hh` is
measured against stale kernels and must be regenerated:

- `syev_prefer_vendor` — the 320 ≤ n ≤ 640 & batch ≥ 128 carve-out
- `syev_prefer_two_stage_values` — n ≥ 512 & batch ≥ 256
- `syev_prefer_vendor_over_cta` / `syev_cta_max_n_for_vectors` — the disabled 1.10–1.15× win
- `syevx_select_algorithm` — the Direct / DirectSubset / Filtered boundaries

Full grid: `n ∈ {32…2048}` × saturated batch × both types × both jobz × every supported
provider. Emit the winner table as **generated code or data**, not as a hand-typed comment
block. That is the durable fix for the staleness that started this whole investigation.

Also settle `syev_cta_max_n_for_vectors`: either relax the `ILUKTests` assertion for
already-converged near-ties, or pin that test's projected-solve provider. It is a
test-tolerance decision blocking a measured win.

### Phase 8 — Adversarial verification **[GPU + CPU]**

For every claimed win from Phases 3–7, spawn independent verifiers prompted to **refute**:

- *Re-measure*: does the win reproduce on the other device, in a fresh process, with the arms
  in reverse order?
- *Saturation*: was the comparison actually at saturation, per `saturation.json`?
- *Name matching*: does the CSV `name` column show exactly the intended benchmarks?
- *Correctness*: does the test set still match the Phase 1 baseline exactly, with no new
  failures and no silently-skipped subtests?
- *Magnitude*: is the win ≥ 1.10× with non-overlapping IQRs?

A finding survives only on a ≥ 2-of-3 majority. Default to refuted when uncertain. Anything
refuted goes back to the relevant phase or is dropped and **reported as dropped** — a phase
that silently drops a result reads as "covered everything" when it did not.

### Phase 9 — Land it **[CPU]**

1. Single source of truth for tuning constants (Phase 3.1), with the retuned values.
2. Regenerated routing tables, machine-generated.
3. `BM_SYEV_RoutingAudit` — the standing benchmark that re-checks every routing cell against
   its runner-up, so the next staleness is a red row rather than an archaeology project.
4. Update `SYEVX_PLAN.md` §13, `JACOBI_EIGENSOLVER_PLAN.md` §13.2, and the comment blocks in
   `syev.hh` / `two_stage_common.hh` / `latrd_lower_panel.cc` with the new numbers **and the
   date and commit they were measured at**. Every table gets a provenance line; that is what
   was missing.
5. Full `ctest` before push. Draft PR.

## 3. Workflow script shape

```js
export const meta = {
  name: 'syev-retune',
  description: 'Find the n=32-512 SYEV regression, pick the small-n kernel, retune and remeasure',
  phases: [
    { title: 'Foundation' }, { title: 'Saturation' }, { title: 'Forensics' },
    { title: 'SmallN' }, { title: 'Midrange' }, { title: 'TwoStage' },
    { title: 'SwitchPoints' }, { title: 'Verify' }, { title: 'Land' },
  ],
}

// A two-slot device lease. This is the whole point: measurement NEVER fans out
// wider than the number of physical GPUs.
const DEVICES = [0, 1]
async function measured(items, makePrompt, phase) {
  const out = []
  for (let i = 0; i < items.length; i += DEVICES.length) {
    const chunk = items.slice(i, i + DEVICES.length)
    const res = await parallel(chunk.map((it, j) => () =>
      agent(makePrompt(it, DEVICES[j]), { phase, schema: MEASUREMENT_SCHEMA })))
    out.push(...res.filter(Boolean))
  }
  return out
}
```

Every measurement prompt must carry, verbatim: the device pin, the saturation batch for that
cell, the exact `name` column expected, the interleaving requirement, and the median-of-5
reporting rule. A measurement agent that returns a bare number without its IQR, its device,
and its batch is treated as failed.

`MEASUREMENT_SCHEMA` requires: `{name, n, batch, type, jobz, provider, device, median_us,
iqr_us, rounds, saturated: bool, notes}`. `saturated: false` rows are reported, never
silently used in a ratio.

## 4. Sequencing and gates

```
Phase 1 (build+baseline)
   |
   +-- gate: CUDA build works, baseline captured
   |
Phase 2 (saturation)  ---- feeds every later phase
   |
Phase 3.0 (env overrides)  <-- enabling code change, blocks 5 and 6
Phase 3.1 (fix shadowing)
Phase 3.2 (archaeology, CPU, parallel with 3.0/3.1)
   |
Phase 3.3 (decisive A/B)
   |
   +-- confirmed --> Phase 5 restores then tunes
   +-- refuted  --> Phase 3.4 bisect, then Phase 5
   |
Phase 4 (small-n bake-off)  -- independent of 3, can run in the other lane
   |
Phase 5 (mid-range constants) -> Phase 6 (two-stage, latrd) -> Phase 7 (switch points)
   |
Phase 8 (adversarial verify)  -- refuted findings loop back
   |
Phase 9 (land)
```

Phases 4 and 3.3 are the only two that can genuinely occupy both GPU lanes at once. Everything
else in the GPU column is sequential by construction, and the plan is honest that this makes
the workflow **long rather than wide**. The parallelism available here is in reading,
archaeology, analysis and verification — not in measurement.

## 5. What would make this fail

Ranked, with the mitigation already folded into the phases above:

1. **Measuring unsaturated.** Mitigated by Phase 2 being a hard dependency and by
   `saturated: false` being a schema field rather than a footnote.
2. **Fanning measurement out across a workflow's default concurrency.** The single most
   likely way this plan produces confident garbage. Mitigated by the two-slot device lease.
3. **Tuning around a disproved hypothesis.** Phase 3.3 is written to be allowed to fail, and
   Phase 3.4 exists for that branch.
4. **A retune that cannot take effect** because of the shadowing. Phase 3.1 before Phase 5.
5. **Substring `--name` contamination.** Mitigated by keying on the CSV `name` column.
6. **Chasing float and shipping for double.** Every phase sweeps both types; the FP64-rate
   caveat is carried into the output text, not just the analysis.
7. **Silent scope reduction** — an agent that measures 3 of 9 cells and reports a clean
   table. Mitigated by requiring dropped cells to be logged, and by Phase 8 checking coverage
   rather than only correctness.
